# 효율적인 LLM 추론

거대 언어 모델(LLM)의 발전 속도는 경이롭지만, 그 성공을 둘러싼 담론은 종종 "특이점"이나 "AGI"와 같은 막연한 낙관론에 치우쳐 있습니다. 하지만 LLM의 폭발적인 성장을 이끈 진짜 동력은 추상적인 미래가 아닌, 지금 이 순간의 **"압도적인 효율성"**에 있습니다.

사실 LLM은 이름과 달리 지난 몇 년간 모델, 하드웨어, 소프트웨어 전반에 걸쳐 엄청난 효율성 개선을 이뤄냈습니다. 이것이야말로 막연한 기대를 넘어 LLM을 현실적인 기술로 만든 핵심입니다.

이 아티클에서는 미래를 이야기하기보다는 과거 효율성에 대한 노력과 기술들을 알아보고자 합니다. 특히 아래에 서술하게 될 기술들은 LLM에서 앞으로 아키텍처가 변하지 않는 이상 절대로 사용되지 않을수 없는 것이므로 

## LLM이 무슨 효율이냐?

LLM 은 말 그대로 거대 언어 모델을 칭하며, "효율적"이라는 단어와 그리 어울리지 않는 것 같습니다. 실제로도 과거의 LLM 모델은 상당히 비효율적이였었죠. (제가 이전에 아티클에서 LLM은 얼마나 좋아졌을까? 을 참고하시거나, https://artificialanalysis.ai/ 의 가성비 부분을 참고하시면 더욱 와닿으실 겁니다.)

하지만 현재의 LLM은 과거의 비효율적을 넘어서 의외로 많이 효율적인 편입니다. 심지어는 생각보다도 더 효율적이죠.

그 근거로는 여러가지가 있는데요 지난 2년동안 LLM API는 약 1000배 정도 저렴해졌다고 [주장하는 글](https://www.snellman.net/blog/archive/2025-06-02-llms-are-cheap/)도 있고, 다른 서비스들보다 LLM 서비스가 더 친환경적이라는 [주장의 글](https://andymasley.substack.com/p/individual-ai-use-is-not-bad-for)도 있습니다.

여기서 LLM API 관련해서는 API 비용이 저렴하다고 해서, 회사들이 낮은 수익성 모델로 삼아서 API 비용이 저렴한 것 아니냐고 할 수 있습니다. 물론 LLM을 서비스하는 대표적인 회사인 OpenAI만 봐도 꾸준하게 매출이 늘긴 하지만 그만큼 꾸준하게 적자를 보고 있는 것을 보면, 이 주장도 사실 틀린 말이 아닙니다. 폭발적으로 성장하려는 기업이므로 공격적인 시장 선점 및 무료 플랜, 대규모 모델 학습, 비디오 생성하는 Sora, 이미지 생성 등등 적자가 안 나는게 사실 이상한 것 같습니다.

그러면 LLM API 가 아닌 순수 모델로 따져볼까요? NVIDIA는 센세이션을 불러 일으킨 Thinking 오픈소스 DeepSeek-R1 671B 모델을 가장 최신 GPU인 B200 8대로 입력을 1,024 토큰, 출력을 2,048 토큰으로 기준으로, 최대 처리량 30,000 Token, 사용자 당 초당 250 Token을 [기록했다고 합니다.](https://resources.nvidia.com/ko-kr-ai-inference/deepseek-r1-inference-performance)

B200 * 8대면 AWS 가격 기준으로 시간당 $65.12 입니다. DeepSeek-R1 공식 API 가격은 위 입출력 토큰 기준으로 입력 50만, 출력 100만 토큰을 기준시 $2.46 달러입니다. 더불어 B200 8대를 빌려 직접 100만 토큰을 직접 뽑아낸다고 했을때 원가는 약 $0.6에 불과합니다. 여기서 100만 토큰이라고 하면 A4 논문 1,500 ~ 2,000장에 해당하는 양이며, 해리포터 전 권에 해당하는 양으로 알려져 있습니다.

물론 B200을 항상 최대 처리량으로 가동해야만 토큰당 약 0.6달러라는 단가가 가능하지만, 그럼에도 불구하고 API 기준 비용이 2.46달러 수준임을 고려하면, 매우 저렴한 편이라고 할 수 있습니다. 심지어 DeepSeek-R1 모델은 LMArena에서 Claude, GPT, Gemini와 경쟁할 정도로 강력한 오픈소스 모델이니까요.

OpenAI가 과거 API로 출시한 [gpt-3.5-turbo](https://openai.com/index/introducing-chatgpt-and-whisper-apis/)는 입력 50만, 출력 100만 토큰을 기준으로 하면 $3 정도니까 과거 대비 얼만큼 발전 했는지 가늠할 수 있을겁니다. 놀라운 건 이것도 3.5 대비 10배 저렴해진 가격이라는 점입니다.

또 다른 재미난 논의로는 속도와 효율성을 넘어서, 가지고 있는 정보의 양이 모델의 크기에 비해 훨씬 크다라는 [논의들](https://news.ycombinator.com/item?id=44442072)도 있습니다. 특히 영어 Wikipedia 텍스트만 해도 156GB에 모든 버전을 합치면 26TB에 달하는 양에 Gemma3 12B 모델 (8.1GB)을 사용 할 때, 모델이 이상한 답을 낼 때도 조금 있었지만, 이 용량에 이렇게나 많은 정보들이 담겨있다는 것에 놀랐다고 말한 사람도 있습니다.

## LLM이 효율적이게 될 수 있었던 이유

그러면 LLM은 어떻게 효율적이게 될 수 있었을까요? 당연하게도 하드웨어의 발전과 소프트웨어 및 알고리즘의 발전을 빼놓을 수 없을 것 같습니다. 저는 특히 이 셋의 발전 중에서 하드웨어의 발전보타 소프트웨어 및 알고리즘의 발전이 훨씬 더 큰 공로를 했다고 생각합니다. 하드웨어의 발전은 FP4 Tensor Cores, HBM, 비동기 트랜잭션, 수행 등등이 있을 것 같습니다. 

소프트웨어와 알고리즘의 발전으로는 대표적으로 Flash Attention, Inflight Batching, KV Cache, Speculative Decoding, Disaggregated inference 등등이 있겠네요, 이번에는 하드웨어의 발전을 이야기하기하면 너무 길어지니 소프트웨어와 알고리즘 중심으로 이야기하고자 합니다.

특히나 Flash Attention, Inflight Batching, KV Cache는 현존하는 모든 LLM 서비스에 들어가며, 이 세 가지는 **절대로** 들어가지 않으면 안되는 것들입니다. OpenAI, Google, Anthropic이 저걸 사용한다고 공식적으로 이야기 한 적은 없지만 이 기술들 없이는 현재와 같은 수준의 서비스 속도와 비용 효율성을 달성하는 것이 거의 불가능합니다.

개인적으로 셋 다 중요하지만, 순위를 매기자면 1위가 KV Cache, 2위가 Flash Attention, 3위가 Inflight Batching 라고 생각하고 있으며, 그 이유는 KV Cache는 알고리즘의 복잡도 자체를 낮추는 근본적인 변화이고, Flash Attention은 하드웨어 최적화를 통한 구현상의 개선이며, Inflight Batching은 서비스 처리량(throughput)을 극대화하는 스케줄링 기술이므로 이렇게 순위를 매겨보았습니다.

그러면 이것들이 좋길래 이러는지 한번 순위대로 알아 봅시다. 

### KV Cache

KV Cache를 이해하기 전에 우선 LLM의 추론 방식을 이해할 필요가 있습니다. 전 아티클에서도 아래와 같이 설명했는데요,

```
입력: 오늘 날씨가
예측 결과: 맑
-------------------
입력: 오늘 날씨가 맑
예측 결과: 습니
-------------------
입력: 오늘 날씨가 맑습니
예측 결과: 다.
```

이런 방식의 추론을 Auto Regressive Model 이라고 합니다. 자기회귀 모델이라고 부르죠. 즉 추론해서 나온 output을 그대로 input으로 넣는 것을 반복하는 겁니다. 이럴 경우 가장 치명적인 문제가 있습니다.

문장이 길어지면 길어질수록 계산량이 기하급수적으로 늘어 난다는 점입니다. 모델은 일반적으로 Input Size가 커지면 커질수록 그 만큼 연산해야 하는 양이 많아지므로 입출력이 길어지면 길어질수록 계산량이 늘어나는 것이죠.

이는 아주 쉽게 해결 할 수 있는데요, **LLM은 모델 구조 상 추론 시 사전에 추론했던 내용을 다시 추론을 안 할 수 있습니다. Self-Attention을 제외하면요.**

Self-Attention을 제외한 나머지 모듈(FFN, MLP)들은 각 토큰을 완전히 독립적으로 처리합니다. 예를 들어 [1,2,3,4,5] -> [11,12,13,14,15] 을 출력하는 모듈일 때 [5] -> [15], [1,5] -> [11,15]로 나오는다는 겁니다. **즉 다른 토큰들이 서로 다른 토큰 출력에 영향을 일절 미치지 않습니다.** 흔히 이걸 Token-wise 연산이라고 합니다. Transformer는 Attention을 제외한 나머지 모듈은 다 Token-wise 연산입니다.

대신 가장 큰 문제는 **Self-Attention**입니다. Self-Attention은 다른 모듈과 달리 새 토큰을 예측할 때 이전 모든 토큰과의 관계를 다시 계산해야 하는 과정이라 모든 입출력이 다 필요로 합니다. 즉 서로 다른 토큰이 영향을 미친다는 것이죠. 이는 당연합니다. 이게 Self-Attention의 핵심이기도 하니까요.

그러면 Attention만 손을 보면 되겠네요? 방법은 간단합니다. Attention이 들어가기 전 기존에 과거에 입력이였던 (Key, Value)들을 저장시켜놓으면 됩니다. 이걸 **KV Cahce**라고 합니다. 기존에 Attention 연산은 모든 Q,K,V 계산하는 방식을 사용했는데, 이는 너무 큰 낭비였었습니다. 그림을 보시면 Q4 * V 만 필요로 했고, 나머지는 사실상 다 필요없는 더미 값에 불과했죠.

그래서 이걸 마지막 입력 값에 해당하는 Q,K,V 와 그 이전의 입력이였던 K, V 들만 있으면 마지막 Q4 * V 들을 뽑아낼 수 있다는 것입니다. 이는 새로운 토큰을 만들어 낼때 연산량이 **O(N²)**에서 **O(N)**로 줄여줍니다.

결론적으로는, Self-Attention을 제외한 모듈은 마지막 토큰만 계산되도 무방했고, 다만 Self-Attention은 모든 토큰이 필요했지만, 과거의 K, V에 해당하는 값만 있으면, 마지막 토큰만 들어와도 Self-Attention 계산을 할 수 있으면서 계산량도 줄일 수 있는 시너지가 있었던 것이였죠.

그래서 KV Cache를 사용한 추론은 처음 입력에 대해 추론이 느리며, 그 다음 토큰 생성하는게 대체적으로 빠른 편입니다. 처음 입력은 KV Cache가 존재할 수 없고, KV Cache를 만드는 입장이라 모든 입출력에 대해서 계산해야하니까요. 그래서 이걸 처음 입력에 대한 추론을 **Prefil**, 그 다음 한개씩 생성하는걸 **Decode** 이라고 부릅니다.

KV Cache는 근데 좀 큰 문제가 있습니다. 그건 바로 KV Cache 를 저장할 때 생기는 용량이 어마어마하게 크다는 겁니다. 이 캐시는 GPU 메모리에 있는 경우가 대부분이므로 비싼 GPU 메모리에 있는건 꽤 치명적입니다.

실제로 Deepseek-R1 671B의 Layer 기준으로는 10만 토큰에 대한 K,V 용량이 400GB (bfloat16)에 육박하며, 새 토큰을 뽑을 때 마다 400GB 메모리를 추가적으로 접근해야 합니다. B200의 GPU 메모리도 180GB인데도 불구하고 400GB면 담을 수도 없고, 여러 GPU로 묶어서 담는다 한 들 한 토큰 생성하는데 200GB 메모리(KV Cache, FP8 기준) + 335GB 메모리(모델 가중치, FP4 기준), 각종 최신 기술을 써도 총 535GB를 접근하는 건 엄청난 메모리 병목입니다.

위와 같은 이유 때문에 LLM 추론이 사실상 HBM이 얼마나 중요한지 알 수 있고, HBM의 성능에 따라 갈리는 기현상도 볼 수 있죠.

이 때문에 KV Cache를 줄이려는 연구도 많이 되고 있습니다. 실제로 Deepseek-R1은 Multi-Head Latent Attention 이라는 것을 통해서 KV 용량을 획기적으로 압축했고, 결과적으로 용량을 기존 대비 57배나 줄여버렸습니다. 덕분에 535GB가 아닌 10GB 언더로 줄일 수 있었죠.

KV Cache를 사용해서 긴 시퀀스에서 말도 안되는 속도 향상을 이루었습니다. 확실히 Attention을 제외한 나머지는 매우 빠른 연산을 할 수 있게 되었고, Attention도 O(N) 까지 줄일 수 있었습니다. 하지만 여기서 더 속도를 빠르게 할 순 없을까요? Flash Attention에서는 기존의 Attention 보다 훨씬 빠른 Attention을 구현했습니다.

### Flash Attention

Flash Attention은 핵심만 설명하자면, GPU 성능을 효율적으로 끌어올리는 Attention 연산이라고 보면 될 것 같습니다. Flash Attention을 설명하기 전에 GPU의 고유 특성을 알아보는 게 좋을 것 같습니다.

CPU에는 RAM이 있고, L3, L2, L1 캐시가 있는데, GPU도 마찬가지로 VRAM이라 하는 DRAM이라는게 존재하고, 그 위 Core에 가깝게 붙어있는 L2 Cache, L1 Cache, Shared Memory 등이 있습니다. L2, L1 Cache 는 Core에 정말 가깝게 붙어있는 매우 빠른 RAM이라고 생각하면 되며, 하드웨어가 자동으로 관리되는 캐시이며, CPU나 GPU는 이 캐시를 개발자가 임의로 조절할 수 없습니다. 근데 GPU에 있는 Shared memory은 뭘까요?

Shared Memory은 프로그램으로 관리할 수 있는 고속 메모리라고 생각하면 될 것 같습니다. 이는 하드웨어에 따라서 최대 20MB 혹은 30MB 사용할 수 있습니다. H200, B200은 총 Shared Memory 용량을 30MB를 가지고 있습니다. (treaming Multiprocessor 132개 * 228KB)

Shared Memory의 메모리 대역폭 속도는 DRAM의 10배 ~ 20배 이상의 속도를 가지며 사실상 행렬 연산에 병목이 없는 수준으로 연산 할 수 있습니다. **여기서 Flash Attention은 이 이점을 사용합니다.**

위 사진같이 기존의 Attention 연산은 HBM 즉 DRAM에서 데이터를 Core로 옮기고 연산하고, 결과를 DRAM에 쓰고 연산하고 를 반복해서 Attention 연산에 6번 왕복의 데이터 전송이 일어났습니다. KV Cache를 써도 사실 KV Cache 용량은 매우 크니 이 또한 메모리 병목에서 벗어날 수 없었죠.

이걸 해결 한 방식은 DRAM에 있는 데이터를 Tiling 하여, 메모리 병목이 거의 없는 Shared memory 에 적재시키고 계산 후에, DRAM으로 빼지 않고 softmax, v 연산을 Shared memory에 한꺼번에 해서 이동으로 연산을 끝내고 DRAM으로 옮깁니다. 최대한 Shared memory에서 계산을 다 끝내는 것이죠.

Tiling을 하는 이유는 Shared memory의 최대 30MB로 허용 용량이 매우 작기 때문에, 입력 Tiling을 잘라서 계산하고 DRAM에 Tiling 연산 된 결과를 차례대로 적재시키는 구조를 가지고 있습니다.

하지만 이렇게 하면 DRAM -> Shared memory으로 전송하는 횟수가 많아져 병목이 생기는 것 아니냐? 할 수 있습니다. 사실은 그림은 설명에 대한 예시지 각 한개의 토큰당 하나의 결과를 내는 방식이 아닌 여러 토큰을 묶어서 계산하는 Tiling 계산을 합니다. 그래서 이 횟수를 크게 줄일 수 있고, 하드웨어의 Shared memory 용량에 따라서 Flash Attention 성능도 달라질 수 있죠.

그리고 NVIDIA GPU는 [DRAM -> Shared memory으로 데이터를 전송하는 동시에 연산을 진행할 수 있습니다.](https://docs.nvidia.com/cuda/ampere-tuning-guide/index.html#asynchronous-data-copy-from-global-memory-to-Shared-memory) 이는 A100 GPU 에서 도입된 기능인데, DRAM에서 Shared memory으로 데이터를 옮기는 건 온전히 DRAM의 대역폭에 국한되는데, 비동기적으로 Shared memory 연산과 데이터 전송을 한꺼번에 할 수 있기 때문에, DRAM -> SRAM 데이터 전송 속도를 Hiding 할 수 있는 겁니다.

이 방식은 행렬곱에서도 유용하게 사용되며 NVIDIA GPU를 가장 극한으로 사용할 수 있는 방식으로 알려져있습니다. 최근은 Flash Attention 3 까지 나왔으며, 3는 NVIDIA H100 GPU의 아키텍처를 최대한 사용하여 하드웨어 이론상 성능의 80%까지 사용 할 수 있었습니다.

이렇게 Flash Attention은 특정 하드웨어를 극한으로 끌어올리는 방식을 사용하여 하드웨어 별로 종속이 있으며, 이게 NVIDIA GPU로 최적화 하는 것에 대해 난항이 있는 이유이기도 합니다.

이렇게 해서 KV Cache로 Decode를 매우 빠르게 했고, Flash Attention으로 Attention 병목을 크게 줄였습니다. 그러면 이제 서비스를 할 수 있는건가요? 아쉽게도 아직 저희는 하나씩 밖에 추론하는 것을 가정했습니다.

이 거대한 모델이 사용자 한 명을 위해서 출력 토큰을 한 개씩 뱉어내는 구조는 굉장히 비효율적이죠, LLM이 아닌 다른 모델들은 배치 추론을 통해서 처리량을 늘리곤 합니다. GPU 특성상 병렬 연산이 커질 수록 연산이 효율적이게 되기 때문입니다.

그러면 모델이 여러 사용자를 커버하기 위해서는 LLM 에서도 배치 추론을 해야 할 것 같습니다. 이제 마지막 Inflight Batching을 알아 봅시다.

### Inflight Batching

**모델에 배치 추론을 하려면 제약이 있습니다.** Input Size가 shape이 동일 해야 한다는 것입니다. 예를 들어 (1, 192) shape의 tensor가 있다고 할 때, 이걸 4개로 쌓아서 (4, 192) 로 만들어서 추론을 하면 이게 배치 추론입니다. (1, 192) 추론을 4번 하는 것보다 (4, 192) 추론을 한 번하는게 훨씬 빠릅니다. 심지어 모델과 GPU에 따라서 (1, 192)의 추론 속도와 (4, 192)의 추론 속도가 동일한 경우도 있습니다. 이럴 경우 처리량이 4배나 차이나는 것이죠, 이는 생각보다 흔합니다.

다만 배치 추론의 문제는 (1, 192) shape와 (1, 256) shape가 있을 때 이런 경우는 합쳐서 배치 추론을 할 수 없습니다. 물론 (1, 192)를 (1, 256) 으로 늘려서 (2, 256) 을 만들거나 반대로 (1, 256)을 줄여서 (1, 192)로 만들어 (2, 192)로 배치를 쌓는 경우가 많습니다. 이 방식을 흔히 전처리라고 부르죠. 많은 모델들은 전처리를 하여 학습을 고정된 shape에 맞게 하는 경우가 많습니다.

LLM에서 배치 추론도 위 방식으로도 배치 추론을 할 수 있습니다. LLM에서는 이 방식을 Static Batching이라고 부릅니다.

Static Batching은 Input에 전처리로 padding을 주어서 입력으로 들어온 가장 큰 사이즈에 맞춥니다. 즉 100, 200, 300의 길이로 세 Input이 들어오면 모두 300으로 token을 맞추고 추론하는 방식이죠, 이 방식이 제일 단순해보이는 방법 처럼 보입니다.

하지만 이 방식은 정말 큰 단점이 있습니다. 세 개중 하나가 미리 끝나도 결과물을 따로 뺄 수 없다는 겁니다. 만약 기술적으로 뺀 다고 해도 현재 추론하고 있는 배치에 다른 input을 넣지 못합니다. 즉 처음에만 GPU가 열심히 작동되고 끝에 갈 수록 GPU를 잘 쓰지 못하게 되는 것이죠. 이는 너무 비효율적입니다.

이 Static Batching의 비효율적인 방식을 완전히 해결 할 수 있는 방식이 바로 Inflight Batching 입니다. Continuous Batching이라고도 불립니다. 이름 그대로 연속 배칭입니다. 이 배치 방식은 추론하고 있는 와중에도 Input을 넣고, 추론이 끝난 것은 Output으로 빼고를 유연하게 하여 지속적으로 GPU를 최대한으로 사용하게 합니다. 이게 어떻게 가능한걸까요?

우리는 이전에 **LLM은 Attention 을 제외한 나머지는 모두 Token-wise 연산이라고 설명하였습니다.** 바로 이 점을 이용하는겁니다. 즉 100, 200, 300의 길이의 세 Input이 들어오면 그냥 이걸 옆으로 붙여서 600의 길이로 만들어서 추론을 합니다. 더군다나 이 방식은 decode 될 때와 prefil이 들어올 때 여부와 상관없이 분간 없이 그냥 concat을 해버립니다.

예를 들어 2개가 decode되고 있으면 거기게 냅다 200을 넣으면 202 개의 추론을 하게 되는 것이죠. 왜냐하면 decode는 하나씩 뱉으니 2개가 되면 2개 + input으로 들어온 200개를 해서 202의 길이를 추론을 하는겁니다. 그러면 그 다음 부터는 3개씩 decode 되는 방식이 되는 거죠.

Attention은 concat한 토큰들을 한꺼번에 다 연산시키면 모든 추론이 섞이므로, 각 request에 대한 파티션 정보가 필요합니다. 그래서 각 토큰 별로 id들이 정해져 있거나, 현재 추론 중인 token의 길이로 파티션을 나누는 경우가 있습니다. 이렇게 파티션으로 분리된 각 request에 대한 Attention를 배치로 연산시켜버립니다.

이 방식은 매우 서비스에 고도화된 방식이라, 일반 PyTorch, TensorFlow에서는 사용할 수 없는 기술입니다. 대신 LLM 추론 고도화 라이브러리인 vLLM, TensorRT-LLM 에서 지원합니다. 사실 Inflight Batching을 사용하려면 Paged KV Cache가 필수적인데, 배치 추론을 할 때 KV Cache의 메모리 효율이 좋아진다라고 간단하게 생각하시면 될 것 같습니다.

## 마무리

위 설명한 각기 다른 Feature들은 분명 같은 사람이 만든게 아닌 서로 다른 사람들이 만든 건데도 불구하고, 이 셋이 기묘하게 얽혀있는 것 같다는 생각이 듭니다.

한번 상상해봅시다. KV Cache가 없는 Flash Attention은 연산 효율성이 떨어져 사실상 그다지 **"Flash"**하지 않았을 겁니다. 아마 있어나 마나한 속도였겠죠. 그만큼 KV Cache 없는 LLM 추론은 상상조차 하기 힘들 정도로 느린 작업입니다.

반대로, KV Cache가 도입되었을 당시에는 Flash Attention이 없었는데, 그때 역시 Attention 연산은 여전히 거대한 병목으로 남아 있었습니다.

또 KV Cache는 LLM이 Token-wise 연산임을 이용해서 효율화를 극대화 했고, 그 덕에 Inflight Batching 기법도 Token-wise 연산임을 이용해서 효율화를 극대화 시켰습니다. 

그리고 아마 Inflight Batching 시에 Flash Attention이 아닌 기본 Attention을 사용했더라면 거대한 Attention 연산을 병렬로 해야므로, 말도 안되고 허무맹랑한 방식이라고 많은 업계 사람들에게 손가락질 받았을 수 있죠.

저는 이 연구들이 비록 각각 다른 배경에서 출발했지만, 서로를 완벽하게 보완하며 결과적으로 극대화된 효율성을 만들어냈다고 생각합니다. 그리고 이러한 상호 보완성은 단순한 우연이 아닐 겁니다. Inflight Batching과 Flash Attention, 그리고 그 이후 등장한 모든 기능들 역시 이전에 쌓여온 기술과 아이디어가 있었기에 가능해진 것들이라고 믿습니다.
